thriveERP — Ground Rules (Draft)
=================================
Status: Draft — expand/edit as the team grows or conventions get decided.

1. GUIDING PRINCIPLE
---------------------
KISS. Build for what we need now. The pluggable/hexagonal structure exists so
we CAN swap pieces later — it is not permission to build every piece now.
If a decision doesn't need to be made this sprint, write it down as deferred
(see DesignLogic.md / ARCHITECTURE.md) and move on.

2. MODULE BOUNDARIES
---------------------
- core-domain must never import a framework (no Spring, no JPA annotations,
  no Jackson). Pure Java only.
- core-app talks to ports (interfaces), never to a concrete adapter class.
- Adapters (persistence, rest, erp-impl, audit) never talk to each other
  directly — everything flows through core-app / core-domain.
- If you're tempted to import adapter-persistence from adapter-erp-impl,
  stop — that's a sign the interaction belongs in core-domain instead.

3. GIT / BRANCHING
-------------------
(fill in once decided — suggested starting point below, edit freely)

Two layers to this, since we're planning per-enterprise customization
(see DesignLogic.md 4.1):

  a) Day-to-day development on the base template:
     - main = always-deployable base template (generic thriveERP +
       trimmed iDempiere)
     - feature branches off main: feature/<short-description>
     - PRs required before merging to main
     - Commit messages: short imperative summary line, body if needed

  b) Per-enterprise customization:
     - client/<client-name> branches off main, for that client's
       deployment-specific changes
     - Non-client-specific fixes made on a client branch should be
       cherry-picked / merged back to main so all clients benefit
     - Decide early (see DesignLogic.md open questions) whether client
       branches should stay config-only or if code/schema divergence
       is expected — that determines how painful merge-back gets over
       time. Revisit once 2-3 client branches actually exist.

  code in the project to test well, so do it.

  should never require a live iDempiere instance.
